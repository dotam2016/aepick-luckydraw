## 2. 전환 중 발견하고 고친 결함 6건

전부 추측이 아니라 계측으로 원인을 특정했다.

### 2-1. Rapier WASM "memory access out of bounds"

**증상** 플레이 시작 직후 크래시. `getRenderState()` → `rbTranslation`에서 죽는다.

처음에 use-after-free로 보고 `destroyed` 가드를 넣었으나 재현이 계속됐다. 인스턴스 생성·해제·초기화
호출을 계측하니 `initCalls: 2`가 나왔다.

**원인** `initPhysics()`가 **결과만** 캐시했다. React StrictMode가 effect를 두 번 실행하고, 두 호출이
동시에 `rapier === null`을 보고 `RAPIER.init()`을 각각 호출한다. 두 번째 init이 WASM 메모리를
교체하면서 이미 만들어진 World가 무효화된다.

**조치** **프로미스를 캐시**한다. 동시 호출이 같은 프로미스를 공유하므로 init은 한 번만 실행된다.

### 2-2. 구슬이 바닥을 뚫고 무한 낙하 (y = −292)

**증상** 하네스에서 구슬 이탈 1581건, 영구 진동 13회차. 두 증상은 같은 원인이었다.

축·페이즈별로 분해하니 y축이 지배적이고 페이즈가 READY였다 — 즉 플레이 시작 전에 이미 벗어나 있었다.

**원인** 생성자의 사전 안정화 300스텝에 속도 상한·격리 안전망을 적용하지 않았고, 구슬을 완전 무작위로
스폰해 두 구슬이 거의 같은 좌표에 놓이면 솔버가 강하게 밀어내 하나가 바닥을 관통했다.

**조치** 세 층으로 고쳤다.
1. 스폰을 **지터 격자**로 변경 — 격자 간격을 지름보다 크게 두고 지터를 여유 안으로 제한
2. 사전 안정화 루프에도 속도 상한·안전망 적용
3. 벽 두께 0.5 → 2 (터널링에 120 units/s가 필요해져 속도 상한 26으로 원천 차단)

최대 초과 거리 **292.6 → 0.441**.

### 2-3. 격리 안전망 오탐 1185만 회

**증상** 안전망이 244,147스텝 동안 1185만 회 발동.

**원인** 클램프 경계에 여유가 없었다. 바닥에 놓인 구슬의 중심은 솔버의 침투 허용치(slop)만큼
반지름보다 살짝 아래에 있어, 정상 상태의 구슬을 매 스텝 되돌리고 있었다.

**조치** 허용치 0.12를 두고 명백한 이탈만 되돌린다. 1185만 → 515회.

### 2-4. 판정 기준이 잘못됨

`contained === 0`을 요구하면 솔버의 순간 오버슈트(0.4 units)까지 실패로 잡힌다.
의미 있는 기준은 **"되돌린 최대 초과가 구슬 반지름보다 작다"** — 화면상 어긋남이 한 프레임도
눈에 보이지 않는다는 뜻이다. 무한 낙하(292 units)는 이 기준에서 걸린다.

### 2-5. AIM 진입 시 집게가 이미 구슬을 물고 있음

**원인** 사전 안정화 동안 집게가 홈 위치(y=8.5)에 있어, 위에서 떨어지는 구슬이 팔·손바닥에 얹혔다.

**조치** 안정화 동안 집게를 박스 위(y = boxHeight + 3)로 치워두고 끝난 뒤 홈으로 내린다.

### 2-6. 렌더 중 부모 setState (React 경고)

**원인** PIN 입력에서 `setPin` 업데이터 함수 안에서 `onAuth`를 호출했다. React는 업데이터를 렌더 중에
실행하므로 부모 setState가 렌더 중에 일어난다.

**조치** 자릿수 완성 감지를 effect로 옮겼다.

### 틀렸던 가설

집게 발끝과 벽 사이 간격(0.83)이 구슬 지름(1.24)보다 좁아 끼임이 발생한다고 보고 `clawMaxX`를
3.4 → 2.9로 줄였다. 안전망 발동은 279 → 257로 거의 변하지 않아 **주 원인이 아니었다.**
다만 기하학적으로 구슬이 통과할 간격을 확보하는 것 자체는 타당해 값은 유지했다.

## 판정 기준 2건 변경 — 근거

무르게 만든 것이 아니라 측정 대상을 바로잡았다.

# 벽 재질 — 프로스티드 아크릴 (2026-08-06)

성능 벤치(docs/07)에서 여유 5.4배가 확인되어 미뤄뒀던 벽 재질 작업을 진행했다.
"절차적 노이즈 수준"이던 벽을 실제 아크릴 패널로 올린다.

## 레퍼런스에서 읽은 것

`reports/refwall/w12.jpg`를 확대해 보면, 벽면에는 **노이즈도 무늬도 없다.**
재질을 만드는 것은 다음 세 가지다.

1. **넓은 세로 그라데이션** — 위가 진하고 아래로 갈수록 옅다. 명도 폭이 크다.
2. **패널 이음선** — 아크릴 시트가 맞닿는 세로선. 대비는 매우 낮다.
3. **시트 단면 하이라이트** — 아크릴 단면이 빛을 물어 벽 좌우 끝에 밝은 세로 띠가 생긴다.

그래서 "노이즈를 더 정교하게" 가는 방향은 **틀렸다.** 처음에 세운 가설(브러시드 결·패널 씸을
잔뜩 넣는다)을 레퍼런스 확대 관찰이 기각했고, 대신 톤과 반사 구조를 손봤다.

가장 중요한 발견은 **명도**다. 레퍼런스의 벽은 중간톤이고, 그래야 구슬이 화면에서
가장 밝은 물체가 된다. 이전 값은 `#fdf2f5 → #fae2e9`로 명도 폭이 5%밖에 안 돼
벽이 사실상 흰 종이였고, 그래서 구슬이 배경에서 떠오르지 않았다.

## 적용

| 항목 | 이전 | 이후 |
|---|---|---|
| 벽 그라데이션 | `#fdf2f5 → #fae2e9` (2스톱, 폭 5%) | `#efc6d6 → #fadfea` (3스톱) |
| 러프니스 | 상수 0.34 | **맵** — base 0.16 · 변화 0.34 |
| 노멀 | 없음 (albedo 노이즈만) | **맵** — 세로결, 강도 0.10 |

# 집게 리깅 — 물리와 화면의 단일 출처 (2026-08-06)

사용자 제보: "아직도 집게가 공을 이상하게 집네" (구슬이 발 사이로 떠올라 몸통을 파고든 상태).

## 원인 — 형상이 두 곳에 따로 하드코딩되어 있었다

`clawGame.ts`(콜라이더)와 `Scene.tsx`(메시)가 각자 팔 형상을 갖고 있었다. 실측 결과:

| | 물리 | 비주얼 |
|---|---:|---:|
| 닫힘 발끝 반경 | 0.574 | **1.345** |
| 열림 발끝 반경 | 0.965 | 0.986 |

구슬 반지름이 0.62이므로 물리는 제대로 감쌌지만(0.574 < 0.62) **화면의 발끝은 반경 1.345,
구슬의 두 배 밖에 서 있었다.** 게다가 물리는 닫을수록 발끝이 모이는데(0.965→0.574)
비주얼은 반대로 벌어졌다(0.986→1.345) — **벌림각의 부호 규약 자체가 서로 반대였다.**

세 번째 값인 구형 조인트 앵커(−0.954)도 물리 발끝(−2.291)보다 1.34 위였다.
그래서 구슬이 발보다 훨씬 위, 집게 몸통 속에 매달렸다.

이전 수정(2026-08-05, `CLOSED_TILT` 0.10 → 0.30)이 물리 쪽만 고쳤기 때문에
증상이 절반만 사라진 채 남아 있었다.

## 조치 — `clawRig.ts` 신설

형상을 한 곳에서만 정의하고 물리·화면이 **같은 함수**를 부른다.
잡는 위치(앵커)도 상수로 적지 않고 발끝 좌표에서 **기하로 유도한다.**

```
발끝 3개가 반경 r에 설 때, 반지름 R인 구슬이 표면으로 닿는 중심 높이 = 발끝 높이 + √(R² − r²)
```

`Scene.tsx`는 마디 길이·굽힘을 JSX에 적지 않고 매 프레임 관절 좌표를 받아 배치만 한다.
`clawGame.ts`는 발마다 캡슐 1개(곧은 막대) → **2개(위팔·아래팔)** 로 나눠 꺾인 팔과 일치시켰다.

### 확정 형상

| 파라미터 | 값 | 근거 |
|---|---:|---|
| 허브 반지름 | 0.16 | 0이면 세 팔이 한 점에서 나와 장난감처럼 보인다 |
| 위팔 / 아래팔 | 0.693 / 0.801 | 레퍼런스의 마디 비율 |
| 팔꿈치 굽힘 | 1.827 rad | 이 굽힘이 있어야 발끝이 구슬 **아래로** 파고든다 |
| 닫힘각 | 1.15 rad | 팔꿈치가 반경 1.15에 서서 구슬(0.62) 실루엣 밖으로 돌아 나온다 |
| 열림각 | 1.60 rad | 아래 두 제약의 교집합 |
| 앵커 y | −1.296 (유도) | 발끝 (r 0.422, y −1.751) + √(0.62²−0.422²) |

열림각을 정한 두 제약:
- 발끝 간격 2×0.975 = **1.95 > 구슬 지름 1.24** — 구슬이 발 사이로 들어온다
- 하강 시 발끝 world y **1.41 > 바닥 구슬 상단 1.24** — 짓눌러 바닥을 뚫지 않는다

첫 시도는 닫힘각 0.85였는데 팔꿈치 반경이 0.88이라 팔이 구슬에 가려 집게가 덩어리로 보였다.
구슬을 제대로 잡긴 했지만 잡은 것이 **보이지 않았다** — 화면으로 확인하지 않았으면 놓쳤을 문제다.

## 함께 잡은 것 — 진자 부호

콜라이더는 `-swayAngle`로, 화면은 `+swayAngle`로 기울고 있었다.
`clawX = carriageX + sin(swayAngle)·L`이므로 양수 = +X 변위이고, 집게의 아래 방향도
+X로 기울어야 한다. 콜라이더 쪽이 틀렸다. 흔들림 각이 작아(≤0.19 rad) 눈에 띄지 않았지만
콜라이더가 화면과 반대로 기울어 있었다.

## 모델 개선

어깨·팔꿈치 너클, 팔꿈치 볼트, **발끝 고무 패드**(금속으로 두면 접점이 하이라이트에 묻힌다),
마디별 테이퍼를 추가했다. 마디는 실린더 + 관절 구체 구성이라 `scale.y`로 길이를 맞춰도
끝이 찌그러지지 않는다.

# 구슬 로고 데칼 (2026-08-06)

마지막 남은 절차적 근사 항목.

## 레퍼런스에서 읽은 것

`reports/ball-ref.jpg` 확대 관찰:

1. 글자가 **크고 읽힌다.** 글자 높이가 구슬 지름의 약 13%.
2. 요소는 **감긴 워드마크 1개 + 사각 스티커 라벨 1개**뿐이다. 어느 각도에서든 한 번에 하나만 읽힌다.
3. 인쇄된 잉크는 캡슐 표면보다 **무광**이다.
4. 구슬이 굴러 앉은 방향이 제각각이라 글자가 뒤집혀 보이는 것도 있다.

## 이전 상태의 문제

텍스처 1024×512가 구체에 감기면 적도 둘레 = 1024px, 즉 **화면상 구슬 지름은 1024/π ≈ 326px**에
해당한다. 레퍼런스 기준 글자 높이는 42px여야 하는데 실제 값은 22px 폰트(대문자 높이 16px ≈ 5%)였다.
화면에서는 글자가 아니라 **얼룩**이었다. 게다가 둘레에 6번 반복해 감아 흰 띠처럼 번졌고,
배지도 2개라 요소가 서로 싸웠다.

## 조치

| 항목 | 이전 | 이후 |
|---|---|---|
| 워드마크 | 22px · 둘레 6회 | **48px · 둘레 2회** |
| 배지 | 2개 (작은 텍스트) | 스티커 라벨 1개 |
| 배치 | 색상당 고정 1종 | **변형 4종** — 구슬마다 다른 자리 |
| 잉크 광택 | 구슬과 동일(0.07) | **러프니스 맵** — 잉크 0.42 |
| 텍스처 | 1024×512 | 512×256 |

**러프니스 맵이 인쇄로 읽히게 하는 결정적 요소다.** 구슬 러프니스가 0.07로 매우 낮아,
글자가 같은 광택이면 "표면에 인쇄된 것"이 아니라 "표면에 투영된 그림"으로 보인다.
three.js는 `material.roughness`에 맵을 **곱하므로**, 재질 러프니스를 잉크 값(0.42)으로 올리고
맵에서 구슬 부분을 `0.07/0.42`로 낮춰 되돌렸다. 색과 무관하므로 변형당 한 장을 전 색상이 공유한다.

### 메모리

색상 8종 × 변형 4종 = 최대 32장이다. 1024×512로 두면 밉맵 포함 **약 89MB**로 과했다.
화면에서 구슬은 150px 안팎이고 512×256이면 지름 환산 163px이라 충분하다 → **약 22MB**.
배치 좌표는 1024×512 설계 좌표계로 적고 그릴 때 축소하므로, 해상도만 바꿔도 치수를 다시 잡을 필요가 없다.

배치 변형 인덱스는 엔진의 시드 rng에서 뽑아 `BallMeta.decalVariant`로 넘긴다 — 재현성이 유지된다.

## 2. "잡힌 공이 집게 안에서 덜그럭거린다"

원인은 **조인트와 콜라이더의 다툼**이었다. 구형 조인트가 구슬을 앵커로 끌어당기는 동안
발 콜라이더는 같은 구슬을 밀어낸다. 매 스텝 두 힘이 싸워 구슬이 미세하게 떤다.

조치: 잡는 동안만 **구슬↔집게 충돌을 끈다**(Rapier 충돌 그룹). 조인트가 이미 위치를 확정하므로
콜라이더가 할 일이 없다. 놓는 순간 복구해 놓친 구슬은 다시 집게에 부딪히며 떨어진다.

`tools/diag/rattle.mts` — LIFT 구간에서 구슬의 집게 기준 좌표를 매 프레임 기록하고,
5프레임 이동평균(=진자 흔들림, §16.2가 요구하는 정상 동작)을 뺀 고주파 성분을 잰다.

# 구슬 팔레트 (2026-08-06)

"구슬이 레퍼런스보다 어둡다"에 대한 후속. 팔레트를 레퍼런스에서 뽑아 맞췄다.

## 도구 — `tools/palette.mjs`

레퍼런스와 현재 화면의 지배색을 **같은 방법으로** k-means 클러스터링해 비교한다.
여기서 나오는 것은 렌더된 색이지 알베도가 아니므로(조명·환경 반사·톤 매핑을 거친다),
양쪽을 같은 방법으로 재고 차이만큼 알베도를 옮긴다.

측정 영역을 넓게 잡았더니 **비중 1위(25.2%) 클러스터가 구슬이 아니라 라벤더 벽**이었다.
벽도 채도가 높아 채도 필터로 걸러지지 않는다 → 더미 안쪽으로 좁혔다.

## 팔레트

레퍼런스 클러스터는 같은 구슬의 밝은 면/그늘 면이 쌍으로 나온다
(예: 빨강 `#e36a79` L65 / `#ac3a51` L45). 이를 합쳐 색 계열과 비중을 뽑았다.

두 가지를 바꿨다.

1. **각 색을 더 밝고 선명하게.** 렌더가 채도를 약 20포인트 떨어뜨리므로 알베도는 그만큼 높게 잡는다.
   어두운 초록(`#4cb85c`)은 레퍼런스에 있는 밝은 라임(`#9ee256`)으로 교체했다.
2. **밝은 색의 비중을 올렸다.** 평균 밝기는 색 자체보다 분포가 좌우한다 —
   이전에는 가장 어두운 빨강이 전체 가중치의 **29%**를 차지했다.

## 진짜 원인은 팔레트가 아니라 조명이었다

팔레트만 밝게 했더니 L은 올랐는데 **채도가 오히려 떨어졌다**(47.3% → 44.0%).
원인을 찾으려 흰 광원을 의심하고 앰비언트를 낮춰봤는데 결과는 정반대였다.

```
amb 0.38 · key 0.45 → S 44.0% · L 57.5%
amb 0.10 · key 0.45 → S 40.5% · L 53.7%   ← 앰비언트만 낮추면 더 나빠진다
amb 0.10 · key 1.40 → S 51.9% · L 58.8%   ← 키 라이트를 올리자 채도가 오른다
```

구슬이 **저조도에 놓여 있어서** 분홍 앰비언트·환경 워시가 확산색을 덮고 있었다.
직접광을 올리면 확산색이 주도해 채도가 산다. 초기 방침("환경광이 셰이딩을 주도한다")이
만든 `keyIntensity: 0.45`가 칙칙함의 실제 원인이었다.

## 스스로 속은 것 — 포화 픽셀을 버리고 통계를 냈다

`key 2.00`에서 S 59.9% · L 64.0%로 레퍼런스(61.8% / 64.9%)와 거의 일치했다.
그런데 그 상태에서 **벽 픽셀의 97.7%가 포화**되어 있었다.

측정 함수가 하이라이트(L>0.92)를 제외하고 있었기 때문에,
**밝기를 올려 픽셀을 날려버릴수록 남은 픽셀의 통계가 좋아 보이는** 착시가 생긴다.
`palette.mjs`에 포화 픽셀 비율을 함께 출력하도록 고쳤다.

포화 없이 얻을 수 있는 최대가 `key 1.40 · wallEmissive 0.30`이다.

| 벽 — 밝기 / 채도 / 포화 | 84.3% / 67.4% / 0% | 91.4% / 60.7% / 69.3% | **85.7% / 64.0% / 0%** |

## ⚠ 미해결 — 값이 먹지 않는 설정들

더 좁히려다 여러 튜너블이 **화면에 거의 영향을 주지 않는다**는 것을 발견했다.

브라우저에서 확인했다. **값은 들어가는데 렌더에 반영되지 않는다.**

유력 가설: `@react-three/postprocessing`의 `EffectComposer`가 렌더러의 톤 매핑·노출을
우회하고 자체 파이프라인으로 그린다(`ToneMapping` 이펙트를 넣지 않으면 노출이 무시된다).
`envMapIntensity`까지 설명되지는 않으므로 별도 조사가 필요하다.

**이것이 해결되기 전에는 이 값들로 룩을 조절하려 하지 말 것.** 구슬 밝기는
`LIGHTING.keyIntensity`로 조절한다. 레퍼런스와의 남은 격차도 여기서 막혀 있다.

# 캐비닛 조명등 (2026-08-06)

사용자 제안: "레퍼런스 박스는 한쪽이 굉장히 밝다. 박스에만 별도 조명을 쓰는 방식으로 검토 가능한가?"

## 측정 — 제안이 맞다

`tools/lightfield.mjs`로 벽 영역을 8×5 격자로 나눠 상대 휘도를 쟀다.

| | 레퍼런스 | 변경 전 |
|---|---|---|
| 명암 대비 (최대/최소) | 1.53~1.75배 | **1.30배** |
| 좌우 비대칭 | **−8.0%p** (왼쪽이 밝음) | **0.3%p** (완전 대칭) |
| 세로 | 위가 밝음 | **아래가 밝음** (반대) |

우리 벽은 비대칭 0.3%p — 사실상 완전 대칭인 균일 발광 라이트박스였다.
(사용자는 우측이 밝다고 했는데 내가 가진 두 프레임에서는 좌측-중앙이 밝다.
방향은 다르지만 "방향성 있는 별도 조명이 있다"는 판단이 핵심이고 그건 정확했다.)

## 원인 — 평평한 벽에 기울기를 만들 수 있는 광원은 하나뿐이다

기존 조명 구성에는 **거리 감쇠가 있는 광원이 바닥 발광용 pointLight 하나뿐**이었고,
그것이 아래에 있어서 벽이 아래쪽만 밝았다. 나머지는 전부 공간적으로 균일하다.

- 방향광(directional) — 평면에서 N·L이 일정하므로 **균일**
- 앰비언트 · 발광(emissive) · 환경맵 — 전부 균일

실측으로 확인했다. 벽 발광을 0.30 → 0.03까지 낮추고 키 라이트를 1.4 → 6.0까지 올려도:

```
발광 0.30 · 키 1.4 → 비대칭  0.3%p · 대비 1.30배
발광 0.03 · 키 6.0 → 비대칭 −0.1%p · 대비 1.23배   ← 오히려 더 평평해진다
```

**조명을 아무리 세게 해도 종류가 틀리면 기울기가 생기지 않는다.**

## 조치

캐비닛 상단 좌측에 **거리 감쇠가 있는 pointLight**를 넣었다(`WALL.boxLight`).
천장 디퓨저 패널 뒤에 실제 광원을 두는 셈이라 물리적으로도 앞뒤가 맞는다.
발광이 높으면 조명 기울기를 덮어버리므로 `wallEmissive`를 0.30 → 0.10으로 낮췄다.
정면벽 텍스처에 굽는 보조 핫스팟도 함께 넣었다(측벽·천장 제외 — 모서리에서 밝기가 튄다).

## 결과

| | 레퍼런스 | 변경 전 | 확정 |
|---|---|---|---|
| 명암 대비 | 1.53배 | 1.30배 | **1.35배** |
| 좌우 비대칭 | −8.0%p | 0.3%p | **−4.2%p** |
| 최대 지점 | 상단 한쪽 | 중앙 | **상좌** ✓ |
| 세로 방향 | 위가 밝음 | 아래가 밝음 | **위가 밝음** ✓ |
| 벽 중간 L / S | 84.3% / 67.4% | — | 82.1% / 54.9% |
| 벽 밝은쪽 L / 포화 | 92.6% / 0% | — | 86.4% / 2.1% |

방향은 잡혔지만 **비대칭은 목표의 절반**이다. 더 밀면 밝은 쪽이 포화된다 —
비대칭 −6.2%p까지 올릴 수 있었지만 그 설정에서는 밝은 쪽 픽셀의 **47%가 포화**됐다.
포화된 영역은 색을 잃으므로(앞서 벽에서 겪은 것과 같은 함정) 포화 없는 쪽을 택했다.

레퍼런스는 밝은 쪽 92.6%를 포화 없이 낸다 = 우리보다 헤드룸이 크다.
더 좁히려면 벽 기저 밝기를 더 낮춰야 하는데, 그러면 구슬 조명과 얽히고
그 조절은 **아직 미해결인 렌더 파이프라인 문제**(노출·환경맵 세기가 먹지 않음)에 막혀 있다.

톤 스윕에서 이상치가 반복해서 나왔다(대비 2.78배, 채도 26% 같은 값).

# 뒷벽의 구슬 그림자 제거 (2026-08-06)

사용자 제보: "볼의 그림자가 뒷쪽 box면에 보이는 게 어색하다(레퍼런스에는 없음). 제거 가능?"

## 원인은 그림자가 아니라 화면공간 AO였다

이름만 보고 캐스트 섀도를 의심했지만 아니었다. 벽의 그림자 수신을 껐다 켜며 재보니
**수치가 완전히 동일**했다.

```
벽그림자 on  · AO on  → 벽 단차 7.4%p
벽그림자 off · AO on  → 벽 단차 7.4%p   ← 캐스트 섀도는 무관
벽그림자 on  · AO off → 벽 단차 2.3%p
벽그림자 off · AO off → 벽 단차 2.3%p
```

(벽 단차 = 벽 위쪽 휘도 − 더미 바로 위 휘도. 그림자 띠가 있으면 커진다.)

범인은 **N8AO**다. 화면공간 AO는 앞 물체 실루엣 주변의 배경 픽셀이 그 물체의 깊이를
샘플링해 어두워진다 — SSAO 특유의 후광이고, 오프라인 렌더인 레퍼런스에는 없는 종류의 인공물이다.

`aoRadius`가 1.0으로 **구슬 반지름(0.62)보다 컸던 것**이 직접 원인이다.
2.5유닛 뒤의 벽까지 AO가 번졌다.

## 조치

| | 이전 | 확정 |
|---|---|---|
| `aoRadius` | 1.0 | **0.30** |
| `aoFalloff`(distanceFalloff) | 1.0 | **4.0** |
| `aoIntensity` | 1.6 | **0.8** |

반경을 구슬 반지름보다 작게 잡아 AO가 구슬끼리의 접촉에만 걸리게 했다.

| | 벽 단차 | 더미 크레바스(하위10%) |
|---|---|---|
| 지적 시점 (r 1.0) | 7.4%p | 34.8% |
| **확정 (r 0.30 · f 4.0 · i 0.8)** | **3.1%p** | 44.7% |
| AO 완전히 끔 | 2.3%p | 47.7% |

AO를 끄면 2.3%p가 하한인데(그건 벽 자체의 세로 그라데이션이다), 확정값은 3.1%p로
하한과 0.8%p 차이다. 화면에서는 AO를 끈 것과 구분되지 않으면서 구슬 사이 접촉 음영은 남는다.

## 도구 버그 — 하마터면 반대 결론을 낼 뻔했다

첫 진단에서 네 조합이 **전부 같은 값**이 나와 "AO도 그림자도 원인이 아니다"로 갈 뻔했다.
원인은 `kiosk-shot.mjs --set`의 값 파싱이었다.

```js
globalThis[k] = Number.isNaN(Number(v)) ? v : Number(v);
```

`Number('false')`는 NaN이라 문자열 `'false'`가 그대로 들어가는데,
**문자열 `'false'`는 truthy**여서 끄려던 옵션이 켜진 채로 측정됐다.
불리언을 먼저 처리하도록 고쳤다.

# 빌드본이 서버에서 백지로 뜨던 문제 (2026-08-06)

사용자 제보: "http://localhost:8788/kiosk/ 아무것도 안 나와".

`/kiosk/`는 **200을 반환하고 있었다.** HTML은 정상적으로 서빙됐고, 비어 있던 것은 화면이었다.

## 원인 1 — Vite `base` 미설정

서버는 빌드 산출물을 `prefix: '/kiosk/'`로 서빙하는데(`server/src/index.ts`),
Vite `base`가 기본값 `'/'`이라 index.html이 루트 절대경로를 가리켰다.

```
빌드 index.html   src="/assets/index-*.js"
실제 요청         http://localhost:8788/assets/index-*.js   → 404
정상 경로         http://localhost:8788/kiosk/assets/...    → 200
```

JS가 로드되지 않으니 `<div id="root">`만 남아 백지가 된다.
**빌드본은 지금까지 한 번도 동작한 적이 없었다** — 검증을 전부 개발 서버(5174)로만 했기 때문에
드러나지 않았다.

## 원인 2 — 런타임 문자열 자산 경로

`base`만 고치면 될 것 같지만 아니다. Vite는 **import한 자산만** base에 맞춰 재작성하고,
평범한 문자열은 손대지 않는다.

```ts
useTexture('/assets/aepick-logo.png')   // 로고
const ATTRACT_VIDEO = '/assets/attract.mp4';   // 어트랙트 영상
```

둘 다 `/kiosk/` 접두사 없이 요청되어 404가 난다.

## 조치

| | 조치 |
|---|---|
| base | `defineConfig(({ command }) => ...)`로 바꿔 **빌드에서만** `'/kiosk/'`. 개발 서버는 `'/'` 유지 — 검증 도구(kiosk-shot·bench·wallsweep)가 전부 `localhost:5174/`를 직접 연다 |
| 런타임 자산 | `apps/kiosk/src/assetUrl.ts` 신설. `import.meta.env.BASE_URL`을 붙인다(개발 `/`, 빌드 `/kiosk/`) |

## 검증

빌드본을 헤드리스로 **끝까지 조작**해 확인했다(200 응답만으로는 동작을 증명하지 못한다).

# 구슬 선명도 — DOF 제거 (2026-08-06)

사용자 지적: "공 샤프니스를 좀 올리는 게 좋을 것 같지 않아?"

## 측정 — 원인은 피사계심도(DOF)

`tools/sharpness.mjs` 신설. 지표는 **라플라시안 분산**이다(이웃 픽셀과의 2차 차분;
경계가 또렷할수록 크고 블러가 걸리면 급락한다).

```
현재 (보케 1.4)   분산  53 · 상위1% 엣지  50.9
보케 0.8          분산  88 ·             64.1
보케 0.4          분산 160 ·             86.6
DOF 끔            분산 311 ·            123.7   ← 6배
블룸 끔           분산  57   (거의 무관)
dpr 2.0           분산  86   (효과는 있지만 DOF만 못함)
```

**DOF가 선명도를 6배 깎고 있었다.** 블룸은 사실상 무관했다.

## 초점 거리를 조절할 수 없다

보케를 0.4로 낮춰도 절반밖에 회복되지 않아 초점면을 옮겨 보려 했는데,
`dofFocalLength`를 0.02 · 0.05 · 0.08로 바꿔도 **결과가 완전히 동일**했다
(미해결 렌더 파이프라인 문제와 같은 증상 — 노출·환경맵 세기에 이어 세 번째다).

초점면을 놓을 수 없는 블러는 깊이 표현이 아니라 그냥 흐림이다. 그래서 **끄기로 했다.**
`QUALITY.high.dof = false` — mid·low는 원래 false였으므로 전 단계가 일관해졌다.

# 렌더 파이프라인 조사 — 값이 먹지 않던 설정들 (2026-08-06)

여러 튜너블이 화면에 영향을 주지 않는다는 것을 여러 작업에서 반복 관찰했다.
원인은 **두 개**였고 둘 다 three.js의 문서화되지 않은 동작이었다.

## 원인 1 — EffectComposer가 톤 매핑을 통째로 무력화한다

three.js r169 `WebGLPrograms.getParameters`:

```js
let toneMapping = NoToneMapping;
if ( material.toneMapped ) {
  if ( currentRenderTarget === null || currentRenderTarget.isXRRenderTarget === true ) {
    toneMapping = renderer.toneMapping;
  }
}
```

**렌더타깃에 그릴 때는 톤 매핑이 강제로 꺼진다.** EffectComposer는 항상 렌더타깃에 그리므로
`gl.toneMapping`·`gl.toneMappingExposure`가 무시된다.

즉 이 프로젝트는 **톤 매핑이 전혀 걸려 있지 않은 상태로 돌고 있었다.**
하이라이트 롤오프가 없으니 밝은 부분이 그냥 잘렸고, 벽 채도를 올리려 할 때마다 부딪힌
포화 한계(벽 픽셀 97.7% 포화, 더미 10~16% 포화)가 전부 이것이었다.

앞서 "ACES → Neutral 교체가 화사함을 만들었다"고 적은 것도 **틀렸다.**
그 교체는 아무 효과가 없었고, 실제 개선은 AO 색 변경에서 나왔다.

**조치**: 컴포저 마지막에 `<ToneMapping mode={ToneMappingMode.NEUTRAL} />` 추가.

## 원인 2 — scene.environment를 쓰면 재질의 envMapIntensity가 무시된다

three.js r169 `WebGLRenderer`:

```js
if ( material.isMeshStandardMaterial && material.envMap === null && scene.environment !== null ) {
  m_uniforms.envMapIntensity.value = scene.environmentIntensity;   // ← 재질 값을 덮어씀
}
```

재질이 자체 `envMap` 없이 `scene.environment`에만 의존하면 `material.envMapIntensity`가
**통째로 버려지고** `scene.environmentIntensity`(기본 1)가 쓰인다.

그래서 프로젝트의 반사 세기 설정이 **전부** 죽어 있었다 —
`ENV.bakedIntensity`(1.9) · `LIGHTING.envIntensity`(1.5) · `DEPTH.wallEnvIntensity`(0.55) ·
`THEME.clawEnvIntensity`(1.15) · 전면유리(0.85). 모두 일괄 1로 동작했다.

**조치**: 베이크 직후 씬을 순회해 각 재질에 `envMap`을 직접 물린다(`Scene.tsx`).

### 카메라를 따로 잡아야 했다

게임 화면은 1080×1344(비율 0.80), 대기화면은 1080×1920(0.5625)이다.

```

거리 27  →  27 × 0.364 × 0.5625 = 5.53                                (여유 0.28)
```

## 루프 이음새

물리는 정확히 주기적이지 않아 끝과 시작이 맞지 않는다. 여분 프레임을 더 찍어
앞부분에 크로스페이드로 녹인다.

```
out[i] = mix(f[N+i], f[i], i/X)   (i < X)
out[i] = f[i]                     (그 외)
```

out[N-1] = f[N-1] 다음이 out[0] = f[N]이라 **원래 이웃한 두 프레임**이 이어진다.
실측 이음새 차 0.833은 클립 내 정상 프레임의 최대 변화(0.718)와 비슷한 수준이다.

## 후속 — 흔들림의 기구가 틀렸었다 (같은 날)

사용자 지적: "영상 확인했는데 아무런 움직임이 없다. 레퍼런스는 처음에 쏟아지고(**쏟아질 때 박스도 움직임**)
그 다음 **박스와 같이** 덜그럭거린다."

다른 레퍼런스 영상(`AQOkIKQO….mp4`)을 실측하니 앞선 판단이 두 군데 틀렸다.

### 1. "레퍼런스 구슬은 정지해 있다"는 결론은 맞지만 결론을 잘못 썼다

구슬은 실제로 박스에 대해 거의 움직이지 않는다. 그런데 **박스 자체가 움직인다.**
캐비닛 상단 프레임의 세로 엣지 위치를 프레임마다 추적했다.

```
정지 구간   x = 36, 36, 36 …        (픽셀 단위로 고정)
버스트 구간 x = 23 ~ 49             (화면폭 270의 ±4.8%)
```

즉 "덜그럭"은 **내용물이 박스와 함께 통째로 흔들리는 것**이었다.
구슬에 개별 충격을 주던 `agitate()`는 기구 자체가 틀렸다 —
세기를 26배 올려도 화면이 거의 변하지 않았던 이유다.

### 2. 흔들림은 상시가 아니라 주기적 버스트다

전체 프레임 변화량을 시간축으로 뽑으니 구조가 드러났다.

```
0.0~1.4s  쏟아짐 (정점 30)
1.4~3.6s  감쇠 → 0.15
3.8~5.2s  버스트 (12.75) → 감쇠
5.2~6.6s  정지 (0.12~0.8)
6.8~8.0s  버스트 (10.86) → 감쇠
```

**약 3초 주기, 1.3초에 걸쳐 잦아드는 감쇠 진동**이고 진동수는 약 **1.9Hz**다.

## 조치 — `attractShake.ts`

감쇠 정현파 버스트로 모델링하고, **카메라를 흔들어** 박스가 움직이게 한다.
`ClawGame.setShakeAccel()`도 만들어 박스 좌표계의 관성력을 구슬에 실을 수 있게 했다.

### 관성력은 껐다 — 화면에 기여 없이 루프만 깨뜨린다

```
관성력 배율   버스트 프레임변화   더미 드리프트(정지A↔정지B)
   0.22            6.70                  2.88
   0.08            6.86                  0.88
   0.03            6.87                  0.77
   0.00            6.87                  0.02      ← 채택
```

보이는 움직임은 **전부 카메라 흔들림**에서 나왔다. 관성력은 더미를 조금씩 재배열해
영상 끝의 더미가 시작과 달라지고 그만큼 루프가 벌어질 뿐이었다.
사용자 설명("박스와 같이")과도 이쪽이 맞다. 기구는 남겨 둔다.

## 결과

| | 레퍼런스 | 확정 |
|---|---|---|
| 버스트 정점 프레임변화 | 12.75 | **12.10** |
| 정지 구간 | 0.15 | 중앙 0.50 · 최소 0.00 |
| 박스 이동 | 화면폭 ±4.8% | 동일(진폭 0.53 월드유닛) |
| 진동수 | 1.9 Hz | 1.9 Hz |
| 주기 | 약 3초 | 3.0초 |
| 더미 드리프트 | — | 0.738 |

루프 이음새 값(12.09)은 결함이 아니라 **버스트 시작이 루프 경계와 겹친 것**이다.
버스트는 원래 급격히 시작하므로(레퍼런스도 0.15 → 12.75) 충격으로 읽히고,
오히려 이음새를 가려 준다.

## 재수정 — 구슬 반응을 되살리고 바닥 라이트바 추가 (같은 날)

사용자 지적: "박스는 흔들리는데 공은 안 움직인다. 그리고 레퍼런스처럼 바닥에 뽀샤시한 조명 추가 가능?"

### 관성력을 껐던 판단이 틀렸다 — 지표가 잘못됐다

앞서 "관성력은 화면에 아무것도 더하지 않는다"고 결론 내렸는데, 근거로 쓴 것이
**전체 프레임 변화량**이었다. 그 값은 카메라 흔들림이 압도해 **구슬 움직임을 볼 수 없는 지표**다.

카메라 흔들림을 끄고 다시 재니 구슬은 분명히 반응하고 있었다.

```
관성력 0.00 → 구슬 움직임 0.017
관성력 0.15 → 0.319
관성력 0.35 → 1.838
관성력 0.70 → 4.339
```

### 레퍼런스와 같은 방법으로 다시 맞췄다

더미 영역을 잘라 **박스 이동을 픽셀 정렬로 보정**한 뒤 프레임 차를 낸다 —
그래야 박스가 움직인 몫이 빠지고 구슬만 남는다.

| | 버스트 중앙 | 정지 |
|---|---|---|
| 레퍼런스 | 8.43 | 0.021 |
| 배율 0.35 | 4.98 | 0.047 |
| **배율 0.70** | **7.42** | **0.155** |
| 배율 1.20 | 11.01 | 0.804 |

`accelScale` 0 → **0.70**. 더미 드리프트가 생기지만 루프 경계가 버스트 시작과 겹쳐 가려진다.

### 바닥 라이트바

바닥 평면의 발광만 올려서는 재현되지 않았다 — 바닥이 더미에 거의 가려져 있기 때문이다.

```
바닥 발광 0.55 → 하단 밝기 67.8%
바닥 발광 5.00 → 77.2%   (9배 올려도 9%p)
```

그래서 **전면·후면 바닥 모서리에 발광 막대**를 놓고 블룸 임계(0.9)를 넘겼다.
구슬 아랫면을 비추는 실제 광원도 함께 둔다(`FLOOR_LIGHT`).

```
라이트바 끔  → 하단 밝기 68.2% · 밝은 픽셀 8.1%
라이트바 켬  → 75.8% · 28.7%
```

### 연쇄 보정

라이트바가 게임 화면의 더미까지 밝혀 레퍼런스를 넘어섰다. `ENV.bakedIntensity`로 되돌렸다.

```
바닥등 + 베이크 1.2 → 더미 S 65.8% · L 72.2%   (레퍼런스 초과)
바닥등 + 베이크 1.0 → S 62.1% · L 69.8%        ← 채택 (레퍼런스 61.8 / 64.9)
```

## 집게도 함께 흔들리게 (같은 날)

사용자 요청: "박스 흔들림에 맞춰서 집게도 같이 흔들리게 해줘."

집게는 케이블에 매달린 진자다. 엔진에 이미 진자 적분이 있으므로
**캐비닛 흔들림 가속도를 구동항에 더하면** 된다 — 새 기구가 필요 없다.

```
θ'' = -(g/L)·sinθ − c·θ' − (a/L)·cosθ
a = 캐리지 가속도 + 캐비닛 흔들림 가속도   ← 후자를 추가
```

구슬이 관성력으로 출렁이는 것과 같은 원리이고 값도 같은 출처(`attractShake`)를 쓴다.

### 집게 몫은 따로 잡아야 했다

구슬과 같은 배율(0.7)을 주면 진자가 `SWAY_MAX_OFFSET`(0.5)에 붙어 **위아래가 잘린 움직임**이 된다.

```
집게 배율 0.70 → clawX 최대 0.500  (상한에 붙음)
집게 배율 0.35 → 0.500             (여전히 붙음)
집게 배율 0.22 → 0.332             ← 채택
```

`SHAKE.clawScale`을 분리했다. 흔들림 폭은 약 ±0.33유닛(박스 폭의 6%)이고,
케이블이 기울며 집게가 로고를 가로질러 좌우로 움직인다.
