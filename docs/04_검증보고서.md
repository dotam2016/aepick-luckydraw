## 2. 자동 플레이 하네스 (§15.1)

### 2.1 구성

`tools/autoplay.mts`는 실제 게임 엔진(`apps/kiosk/src/game/clawGame.ts`)을 렌더링 없이
가상 클럭(1/60초 고정 스텝)으로 구동한다. 서버는 실제로 호출한다 — 세션 생성·추첨·지표
전송·결과 조회가 모두 운영 경로와 동일하다.

- 세션은 테스트 모드로 만들어 재고·통계를 오염시키지 않는다.
- `forceTier`로 6개 등급을 순환시키고, 등급 한 바퀴마다 연출 모드를 바꿔 **6×2 전 조합**을 커버한다.
- 실제(비테스트) 세션 40회를 섞어 재고 예약·코드 발급 경로도 확인한다. 당첨 시 무효 처리로 재고를 복원한다.

### 2.3 하네스 자기 검사

통과만 하는 검증 도구는 아무것도 보증하지 못한다. `--fault N` 옵션으로 지정 비율의
회차에서 엔진에 넘기는 `win` 값을 뒤집어 "클라이언트가 서버 결과를 무시하는 버그"를
인위적으로 만들고, 하네스가 이를 검출하는지 확인했다.

| 판정 | 결과 |
|---|---|
| A안에 주입한 결함을 100% 검출 | ✅ 12/12 |
| 정상 회차 오탐 | ✅ 0건 |
| B안은 결함을 주입해도 연출이 깨지지 않음 | ✅ 0건 |

세 번째 줄은 실패가 아니라 **B안의 구조적 특성을 실측으로 확인한 것**이다. B안은 결과와
무관하게 항상 획득하므로, `win` 값을 잘못 받아도 획득 연출 자체는 달라지지 않는다.
즉 물리-결과 불일치라는 실패 모드가 원천적으로 존재하지 않는다. 이는 기획서 §4.3이
B안의 장점으로 적은 내용과 일치한다.

판정 기준은 엔진의 자체 점검(`verifyOutcome()`)이 아니라 **서버가 확정한 결과**를 쓴다.
엔진 자체 점검은 자신이 받은 값과 비교하므로 잘못 받은 경우를 잡지 못한다.

## 3. API E2E (§16.1 / §16.3)

`tools/e2e.mjs` — 64항목 전부 통과. 스위트는 시작 시 상태를 초기화하므로 반복 실행해도
같은 결과가 나온다 (연속 2회 확인).

주요 확인 항목:

| 영역 | 확인 내용 |
|---|---|
| 결과 은닉 (§11.1) | 세션 생성 응답에 등급 문자열·경품명·코드가 없음을 정규식으로 검사. 잘못된 `resultToken`은 403 |
| 멱등성 (§10.2) | 동일 키 재요청은 같은 세션·같은 연출 계약 반환. **동시 8회 요청 → 세션 1개만 생성** |
| 상태 전이 (부록 B) | 전이 순서 `CREATED→DRAWN→PLAYED` 로깅 확인. 미완료 세션 존재 시 신규 Start 409 차단 |
| 재고 동시성 (§16.3) | **재고 1개에 동시 12회 당첨 시도 → 당첨 1건, 잔여 0, 음수 없음.** 코드 중복 발급 0 |
| 지급 (§6.4 / §10.3) | 코드로 지급 완료 → 큐에서 제거 → 재제시 409 `ALREADY_CLAIMED` (최초 지급자·시각 반환) |
| 설정 게시 (§9.3) | 합계 ≠ 100.000% 거부, 사유 없는 게시 거부, **진행 중 세션은 이전 `rule_version` 유지** |
| 무효 처리 (§5.5) | 사유 필수. 예약 재고가 available로 복원. 무효 세션은 지급 불가 |
| 운영 통제 (§13) | 긴급 중지·행사 OFF에서 신규 세션 409 차단 |
| 감사 (§14) | 설정 게시·재고 조정·지급·무효가 사유와 함께 감사 로그에 기록 |

## 5. 정책 변경 권고 — §5.4 페이싱 기본값

시뮬레이터로 방문자 900명 × 200회 반복을 돌려 시간대별 당첨률 곡선을 측정한 결과,
**기획서 §5.4의 기본값(페이싱 대상 1~3등)으로는 후반 붕괴가 전혀 완화되지 않는다.**

| 페이싱 대상 | 첫 시간 → 마지막 시간 당첨률 |
|---|---|
| 없음 | 68.9% → 17.6% |
| **1~3등 (기획서 기본값)** | **62.9% → 17.8%** |
| 1~5등 | 61.4% → 43.4% |

원인은 1~3등이 아니라 **4등이 597번째 방문자에서 100% 확률로 소진**되는 것이다.
물량이 많은 등급이 곡선을 지배하므로 페이싱은 전 등급에 걸어야 한다.

§5.4는 "4~5등은 수량이 많아 페이싱 없이 자연 소진을 허용한다"고 적었는데, 이 전제가
성립하려면 4~5등 재고가 예상 참여자 수를 충분히 넘겨야 한다. 실제 경품 수량이 확정되면
시뮬레이터로 재검증할 것을 권고한다.

서버 기본값은 문서와의 일관성을 위해 1~3등으로 두었고, 어드민 → 확률 설정에서 변경 가능하다.

```bash
npm run sim -- --pacing-tiers t1,t2,t3,t4,t5   # 비교 실행
```
