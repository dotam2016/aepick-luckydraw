# 비주얼 스파이크 결과 — Three.js로 레퍼런스 룩에 도달 가능한가

**질문** 롯데면세점 Lucky Picker 수준의 비주얼을 별도 3D 엔진(Unity) 없이 웹으로 구현할 수 있는가
**전제** 집게 이동은 1축(X) 유지. 비주얼 검토 후 수정 가능하도록 모든 파라미터를 조절 가능하게 구성
**결과물** `apps/spike-3d` (별도 워크스페이스 — 검증된 키오스크 앱은 건드리지 않음)

```bash
npm run dev -w @aepick/spike-3d     # http://localhost:5175
node tools/shot.mjs --out reports/x.png   # 헤드리스 1080×1920 캡처
```

---

## 1. 결론

**Unity는 필요하지 않습니다.** Three.js로 레퍼런스와 같은 성격의 룩에 도달했습니다.

| 요소 | 도달 여부 |
|---|---|
| 벽 색·그라데이션, 발광 시안 바닥 | ✅ 거의 일치 |
| 넓고 부드러운 하이라이트 | ✅ 일치 (환경광 주도로 전환한 뒤) |
| 골이 파인 은색 캡슐 | ✅ 일치 (절차적 지오메트리) |
| 구슬 틈의 앰비언트 오클루전 | ✅ 일치 (N8AO) |
| 피사계심도 | ✅ 동작 (레퍼런스보다 약함) |
| 팔레트 인상 | ◔ 근접 (마젠타가 아직 다소 눈에 띔) |
| 모션 블러 | ✗ 미구현 (정지 프레임 평가라 제외) |
| 로고 데칼 | ◔ 메커니즘 확인 (브랜드 에셋 없음 — 임시 문자로 대체) |

비교 이미지: `reports/cmp-final.jpg` · `reports/cmp-depth.jpg`

레이트레이싱·GI·SSR·굴절 중 **어느 것도 필요하지 않았습니다.** 레퍼런스에 그런 요소가 애초에 없기 때문입니다.

## 2. 가장 중요한 발견 — 2D 물리로는 이 룩이 안 됩니다

`reports/cmp-depth.jpg`

구슬 40개를 같은 조건에서 깊이만 바꿔 렌더했습니다.

| 설정 | 결과 |
|---|---|
| **depth = 1** (현재 `matter-js` 2D 물리와 동일한 평면 배치) | 구슬이 z=0 평면에 갇혀 **위로 쌓여 벽을 만듭니다.** 캐비닛 절반을 채우는 구슬 벽 — 볼 피트로 읽히지 않습니다 |
| **depth = 3** (3D 물리) | 바닥에 얕게 퍼진 자연스러운 더미. 레퍼런스와 같은 구조 |

2D 물리에서 이 룩을 내려면 구슬 수를 크게 줄여야 하고, 그러면 더미가 빈약해집니다. 즉 **구슬 수와 더미 형태를 동시에 만족시킬 수 없습니다.**

### 이것이 "1축 유지"와 충돌하지 않습니다

두 개념을 분리해야 합니다.

- **집게 이동축** — 게임성. 1축(X) 유지. 조작 UI·조준 시간·하네스의 catchX 커버리지 모두 현재 설계 그대로.
- **물리 차원** — 비주얼. 구슬 더미는 3D여야 합니다.

**권고: 3D 물리 + 1축 집게.** 집게는 X로만 움직이고 Y로 하강하며, 구슬만 3D로 쌓입니다. 레퍼런스 룩을 얻으면서 게임 설계(§4.1, 조준 12초, 드래그 바)는 그대로 유지됩니다.

부수 효과로 `ClawGame.pickTargetBall()`의 근접 판정에 z 항이 하나 추가되는 것 외에 상태머신·타이밍·서버 계약·검증 하네스 구조는 전부 유지됩니다. Rapier 3D는 WASM이라 **Node에서 실행되므로 640회 자동 플레이 하네스도 그대로 살아남습니다.**

## 3. 두 번째 발견 — 캐비닛 비율을 바꿔야 합니다

레퍼런스 캐비닛은 **가로형**입니다(큰 화면이 가로 대형 디스플레이). 우리 키오스크는 **1080×1920 세로형**입니다.

세로 프레임에 박스 높이를 맞추면 가시 폭이 `높이 × 0.5625`로 좁아지므로, 레퍼런스 비율(가로로 넓은 박스)을 그대로 쓰면 좌우가 잘립니다. 스파이크에서 확정한 비율은 다음과 같습니다.

| 항목 | 값 | 근거 |
|---|---|---|
| 박스 폭 : 높이 : 깊이 | 9.5 : 19 : 5 | 세로 프레임을 채우고 좌우 벽이 살짝 보이는 지점 |
| 카메라 | fov 50, pos (0, 11.5, 20.5), target (0, 8.6, 0) | 살짝 내려다보는 각. 프레임 하단이 바닥선에 오도록 |
| 전면 하단 베젤 | y −1.6, 높이 3.4 | 프레임 아래 빈 공간을 가림 |

## 4. 검증 중 발견하고 고친 것

스파이크 과정에서 나온 실제 문제들입니다. 값을 눈대중으로 맞춘 것이 아니라 원인을 찾아 고쳤습니다.

| # | 증상 | 원인 | 조치 |
|---|---|---|---|
| 1 | 구슬 일부가 **검게** 렌더 | 데칼 텍스처 배경이 투명(RGB 0)이었고, three의 `map`은 `material.color`에 **곱해진다**. 0을 곱하면 검정 | 텍스처 배경을 구슬 색으로 채우고 `color`를 흰색으로 둠 (`ballTexture()`) |
| 2 | 화면 전체 흰색 과노출 | 벽을 `MeshStandardMaterial`로 두어 조명을 받게 함 → 구슬을 밝히려 광량을 올릴 때마다 벽이 먼저 날아감 | 벽을 `MeshBasicMaterial`(라이트박스)로 전환. 벽 색과 구슬 조명을 독립 제어 |
| 3 | 금속이 **검은 크롬**처럼 납작함 | 환경맵 면이 작아 반사할 밝은 영역이 부족 | Lightformer 면을 크게 |
| 4 | 금속이 **흰 플라스틱**처럼 납작함 | 반대로 사방을 균일하게 밝게 두면 명암 대비가 사라짐 — 크롬은 어두운 영역이 있어야 크롬으로 읽힘 | 위는 강하게, 측면·뒤는 어둡게 하는 방향성 환경맵 |
| 5 | 하이라이트가 작고 단단해 플라스틱처럼 보임 | 방향광이 셰이딩을 주도 | key 1.7 → 0.45, env 0.7 → 1.5. **환경광이 셰이딩을 주도하게 전환** — 이 변경이 레퍼런스 성격에 가장 크게 기여 |
| 6 | 골 파인 구슬의 극 근처가 지저분함 | 방위각 기반 변위가 극에서 수렴 | `sin(φ)`로 진폭 감쇠 |
| 7 | 페이지가 흰 화면 | Vite 의존성 캐시가 stale (`504 Outdated Optimize Dep`) | 캐시를 Dropbox 밖으로 이동 — 동기화가 `.vite`를 잠가 `EBUSY` 발생 |
| 8 | 브라우저 패널이 표시되지 않으면 캔버스가 렌더되지 않음(300×150) | 페이지가 컴포지팅을 안 함 | 헤드리스 Chrome 캡처 도구(`tools/shot.mjs`) 작성. 재현 가능한 1080×1920 캡처 확보 |

### 되돌린 것

라이트그레이 색을 추가하고 금속 비율을 26%로 올린 시도는 **역행**했습니다 — 흰색·은색이 화면을 지배해 레퍼런스보다 무거워졌습니다. 되돌렸습니다. (금속 18%, 라이트그레이 제거)

### 측정으로 확인한 것

후처리가 실제로 동작하는지 추측하지 않고 이미지 차분으로 검증했습니다.

| 효과 | 검증 |
|---|---|
| N8AO | on/off 평균 절대차 **32.5**, 137만 픽셀 변화 → 동작 |
| DepthOfField | on/off 평균 절대차 **7.35**, 42만 픽셀 변화 → 동작 |

## 5. 확정된 시작값

`apps/spike-3d/src/config.ts`의 `DEFAULT_CONFIG`. 패널의 "설정 복사"로 언제든 현재 값을 JSON으로 꺼낼 수 있습니다.

```
구슬        40개, r 0.66, 더미 깊이 3겹, 금속 비율 18%
박스        9.5 × 19 × 5, 벽 #d6cdf2→#bdb2e8 (Basic), 바닥 발광 #7ff0e8
재질        roughness 0.32 / 금속 0.42, clearcoat 0.4, 골 9개 깊이 0.095
조명        key 0.45 · fill 0.18 · ambient 0.22 · env 1.5  ← 환경광 주도
후처리      Bloom 0.32/th 0.9 · DOF bokeh 6 · AO 2.2/r 1.0
카메라      fov 50, (0, 11.5, 20.5) → (0, 8.6, 0)
```

팔레트는 레퍼런스 분포를 세어 가중치를 부여했습니다 (빨강 5.5 / 흰 3.0 / 파랑 3.0 / 초록 2.5 / 노랑 2.0 / 퍼플 1.5 / 틸 0.8 / 마젠타 0.6). 균등 분포로 두면 마젠타·라임이 과하게 튀어 전체 인상이 달라집니다.

## 6. 성능 — 아직 답이 안 나왔습니다

| 측정 | 값 | 신뢰도 |
|---|---|---|
| 개발 기기, 실제 브라우저, dpr 1.5, 구슬 34개, Bloom+DOF+AO 전부 on | **60fps** | 직접 관측. 단 데스크톱 GPU |
| 헤드리스 캡처 | 0fps 표시 | **무의미** — SwiftShader 소프트웨어 렌더 |
| Android 키오스크 실기기 | **미측정** | 기기 미확정 (§19 P0) |

레퍼런스의 3D는 폰이 아니라 **큰 화면을 구동하는 데스크톱급 장비**에서 돌아갑니다(폰은 D-pad 컨트롤러). 우리는 Android 태블릿 1대에서 같은 것을 해야 하므로 **성능 마진이 저들보다 좁습니다.** 이것이 이 프로젝트의 남은 최대 불확실성입니다.

대비책은 이미 구조에 넣어 두었습니다.

| 단계 | 구성 |
|---|---|
| high | dpr 1.5, Bloom + DOF + AO, 그림자 |
| mid | dpr 1.2, Bloom + AO, DOF 제거, 그림자 |
| low | dpr 1.0, Bloom만, AO는 박스에 베이크, 그림자 없음 |

그리고 **대기화면은 프리렌더 영상 루프**로 처리하면(레퍼런스가 쓴 방식) 가장 눈에 띄는 화면을 오프라인 품질로 확보하고 실시간 부담은 플레이 구간에만 걸립니다.

## 7. 남은 격차 — 엔진이 아니라 아트입니다

| 격차 | 해결 방법 |
|---|---|
| 레퍼런스 구슬이 약간 더 작고 많음 | 구슬 수를 40 초과로 올리면 근접. 단 기획서 §7.3의 25~40 범위를 넘김 → **정책 결정 필요** |
| 마젠타가 아직 눈에 띔 | 가중치 추가 하향 또는 제거 |
| 금속의 어두운 밴딩이 레퍼런스보다 약함 | 환경맵 대비 추가 조정 |
| DOF 블러가 레퍼런스보다 약함 | bokehScale 상향 (성능과 트레이드오프) |
| 로고 데칼 | **공식 브랜드 에셋 필요** (§19 P0) |
| 모션 블러 | 실시간에서는 생략 또는 속도 기반 스트레치로 근사 |
| 3발 집게 디테일 | 현재 프리미티브 조합. 실제 모델은 Blender→glTF로 교체 |

## D.1 Aepick 테마

브랜드 토큰은 `Aepick 6core Value`(Beauty DNA) 프로젝트의 확정값을 그대로 가져왔다.
단일 핑크 시스템이며 로고는 소문자 `aepick` 워드마크다.

| 토큰 | 값 | 적용 |
|---|---|---|
| accent | `#f25c7c` | 집게, 조작부 버튼 |
| bg1 → bg0 | `#fdf2f5` → `#fae2e9` | 캐비닛 벽 그라데이션 |
| accentSoft | `#fbd7e0` | 레일, 하단 베젤 |
| gold | `#e8b84b` | 초기에 바닥 발광으로 썼으나 빈 박스에서 화면을 지배해 크림톤(`#f8ead2`)으로 완화 |

레퍼런스는 연보라 + 시안 바닥이었다. 두 테마를 패널에서 즉시 전환할 수 있게 남겨 두었다.

## D.2 조작부

레퍼런스 컨트롤러의 시각 언어(광택 금속 베젤 + 유리 버튼 + 장식 아이콘 + 중앙 타이머)를 따랐다.
게임 필드는 상단 1080×1344, 조작부는 하단 1080×576이다.

**축 처리에서 판단이 필요했다.** 레퍼런스는 4방향 D-pad지만 우리는 1축을 유지한다.
동작하지 않는 상·하 버튼을 그려두면 사용자가 누르고 반응이 없어 고장으로 인지하므로,
1축에서는 상·하를 아예 그리지 않고 좌·우 두 버튼만 같은 스타일로 둔다.

`inputAxes` 값으로 두 안을 즉시 전환할 수 있다 (`reports/cmp-axes.jpg`).
3D 물리로 전환하면 2축도 기술적으로 가능해지므로, 게임성 측면에서 원하시면 플래그 하나로 바뀐다.
단 2축은 조준 시간·조작 안내·자동 플레이 하네스의 커버리지 축이 함께 변경되어야 한다.

## D.3 대기화면 영상 — 직접 렌더 가능하다

`tools/render-attract.mjs`로 **같은 Three.js 씬에서 프레임 단위로 렌더해 mp4로 인코딩**한다.

```bash
node tools/render-attract.mjs --seconds 8 --fps 30 --steps 8 --out reports/attract.mp4
node tools/render-attract.mjs --cfg '{"ballCount":140,"dpr":2}'   # 오프라인이므로 상향 가능
```

결과물: `reports/attract.mp4` (8초 · 1080×1920 · 30fps). 구성은 빈 박스 → 구슬 낙하 → 정착이다.

오프라인 렌더의 이점:
- 실시간 60fps 예산에 묶이지 않으므로 구슬 수·해상도·후처리를 실기기 한계 이상으로 올릴 수 있다
- `window.tickSim(n)`으로 시뮬레이션을 명시적으로 진행시키므로 **같은 시드 + 같은 스텝 = 같은 영상**

### 렌더 중 고친 문제

| 증상 | 원인 | 조치 |
|---|---|---|
| 프레임당 15초 (6초 영상에 25분) | 헤드리스 Chrome이 SwiftShader(소프트웨어 GL)로 폴백 | `--use-angle=d3d11`로 실제 GPU 사용. 8초 영상 3분 30초로 단축 |
| 영상 앞부분에 낙하가 안 담김 | 캡처 시작 전 대기(환경맵 생성) 중 시뮬레이션이 자동 진행돼 이미 정착 | `window.__offlineRender` 플래그로 자동 진행 차단, 명시적 스텝만 수락 |
| 낙하가 6초 안에 끝나지 않음 | 완화 솔버의 프레임당 중력 진행량이 너무 작음 | 프레임당 스텝 2 → 8 |
| 프레임 폴더 삭제 실패(EBUSY) | Dropbox 동기화가 파일을 잠금 | 프레임을 시스템 임시 폴더에 쓰도록 변경 |

### 한계 — 연출 구성의 범위

현재 렌더 가능한 것은 **고정 카메라 + 구슬 낙하 + 집게 대기 흔들림**이다.
추가하려면 각각 작업이 필요하다.

| 연출 | 상태 |
|---|---|
| 구슬 낙하·정착 | 가능 (구현됨) |
| 카메라 이동(푸시인·오빗) | 미구현. 키프레임 보간 추가로 가능 |
| 모션 블러 | 미구현. 후처리 또는 프레임 누적으로 가능하나 비용 큼 |
| 집게 하강·집기 데모 | 미구현. Rapier 전환 후 실제 게임 시퀀스를 그대로 녹화하는 편이 낫다 |
| 자막·UI 오버레이 | DOM 오버레이를 켠 채 캡처하면 그대로 들어간다 |

품질은 **실시간 엔진 렌더 품질**이다. Blender/Cycles 같은 오프라인 레이트레이서 수준은 아니다.
다만 레퍼런스 어트랙트도 그 수준을 넘지 않으므로 목표에는 부합한다.

## D.4 PC 타깃으로 바뀐 것

기획서 v1.1은 Android 세로형 키오스크를 전제로 썼다. PC로 확정되어 아래가 바뀐다.

| 항목 | v1.1 (Android) | PC |
|---|---|---|
| 성능 예산 | 태블릿 GPU — 최대 불확실성 | 데스크톱 GPU — 레퍼런스와 동일 조건 |
| 구슬 수 | 25~40 (§7.3) | **78 이상 가능** |
| 후처리 | 단계 축소 필요 예상 | Bloom + DOF + AO 전부 유지 가능 |
| 키오스크 모드 | Device Owner 프로비저닝 (§19 P1) | Windows 키오스크 모드 / 셸 대체 |
| 배포 | APK | 브라우저 키오스크 실행 또는 Electron 패키징 |
| 2차 범위 | Kotlin WebView 쉘 | 불필요 |

기획서 §1.2, §14 성능, §19 확정 항목을 v1.2에서 갱신해야 한다.
