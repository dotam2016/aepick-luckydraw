# 렌더 성능 벤치마크 결과

측정 도구: `tools/bench.mjs` · 측정일 2026-08-06 · 개발 PC 기준
해상도 1080×1920 · 조합당 8초 · 헤드리스 Chrome + ANGLE(D3D11)

> 이 문서의 수치는 **개발 PC** 값이다. 설치 PC가 확보되면 같은 명령을 그대로 돌려
> 표를 교체하면 된다. 판정 로직까지 스크립트에 들어 있으므로 추가 해석이 필요 없다.

```bash
node tools/bench.mjs --seconds 8 && node tools/bench.mjs --seconds 8 --vsync
```

---

## 1. 왜 두 번 재는가

한 번만 재면 결론이 나오지 않는다.

- **vsync ON**(실사용 상태)에서는 모든 조합이 60fps에 붙는다. 여유가 5배인지 1.05배인지 알 수 없다.
- **vsync OFF**로 풀면 헤드룸은 보이지만, 300~500fps로 돌면서 GPU 큐 압력 때문에
  실사용에 존재하지 않는 300~570ms 스파이크가 섞인다.

그래서 **헤드룸은 vsync OFF에서, 끊김 여부는 vsync ON에서** 읽는다.
아래 §4에 이 스파이크가 인공물이라는 근거가 있다.

## 2. 효과별 단가 (vsync OFF · 베이스라인에서 하나씩만 켬)

| 조합 | 중앙 프레임 | 단가 | 비고 |
|---|---:|---:|---|
| 베이스라인 (효과 전부 off) | 1.8 ms | — | 물리 + 지오메트리 + 머티리얼만 |
| + AO (N8AO) | 2.4 ms | **+0.60 ms** | 가장 비싼 효과 |
| + Bloom | 2.8 ms | +1.00 ms | 측정 편차 있음(0.6~1.0) |
| + DOF | 2.6 ms | +0.80 ms | |
| + 그림자 | 2.0 ms | +0.20 ms | |
| + 전면유리 | 1.8 ms | +0.00 ms | 사실상 공짜 |
| + 접지 그림자 | 1.9 ms | +0.10 ms | 사실상 공짜 |
| **전부 on (현재 배포 설정)** | **3.1 ms** | **+1.30 ms** | 부분 합(2.7)과 일치 — 효과는 가산적 |

**읽는 법**: 60fps 예산은 16.7 ms다. 현재 배포 설정이 3.1 ms이므로 **여유 5.4배**.
효과를 전부 합쳐도 1.3 ms — 즉 이 씬의 비용은 효과가 아니라 베이스라인(1.8 ms) 쪽이다.
성능 때문에 효과를 뺄 이유는 현재 없다.

## 3. 나머지 축 (vsync OFF)

| 품질 프리셋 | 중앙 프레임 | | 구슬 수 | 중앙 프레임 | | 렌더 배율 | 중앙 프레임 |
|---|---:|---|---|---:|---|---|---:|
| high | 3.2 ms | | 40 | 2.6 ms | | dpr 1.0 | 3.1 ms |
| mid | 2.8 ms | | **78 (현재)** | 3.2 ms | | dpr 1.25 | 3.1 ms |
| low | 2.6 ms | | 110 | 3.8 ms | | **dpr 1.5 (현재)** | 3.2 ms |
| | | | 140 (상한) | 4.3 ms | | | |

세 가지 모두 예산 대비 미미하다.

- **품질 프리셋의 실효**: high→low로 낮춰도 3.2 → 2.6 ms, 0.6 ms밖에 못 번다.
  §13 자동 축소는 이 기기에서는 사실상 의미가 없다. 저사양 PC에서 베이스라인 자체가
  무거워질 때 의미가 생기는 장치다.
- **구슬 수**: 40 → 140으로 3.5배 늘려도 2.6 → 4.3 ms. 예산의 26%.
  **구슬 수는 성능이 아니라 연출로 정하면 된다.** 기획서 §7.3 상한 140은 안전하다.
- **렌더 배율**: 1.0 → 1.5가 3.1 → 3.2 ms로 거의 무차이. 이 씬은 픽셀 셰이딩이 아니라
  드로우콜·물리 쪽에 묶여 있다는 뜻이다. dpr을 낮춰서 얻을 것이 없으므로 1.5를 유지한다.

## 4. 끊김 판정 (vsync ON · 실사용 상태)

**전 조합 · 8초 · 25 ms 초과 프레임 0%.** 최악 프레임은 어느 조합에서도 17.3~19.8 ms로,
60Hz 한 틱(16.7 ms)을 실제로 놓친 프레임이 없다.

| | vsync OFF | vsync ON |
|---|---|---|
| 전부 on — 최악 프레임 | 570.3 ms | **17.9 ms** |
| 전부 on — 끊김 비율 | 4.65% | **0%** |
| 구슬 140 — 최악 프레임 | 378.9 ms | **18.2 ms** |

vsync OFF에서만 보이던 300~570ms 스파이크는 60Hz로 고정하면 완전히 사라진다.
프레임 예산이 5배 남는 상태에서 500fps로 돌 때만 나타나므로 **벤치마크 인공물**이며,
실사용 프레임 저하가 아니다. (스파이크가 AO를 켠 조합에 집중된 것도 같은 이유로 설명된다 —
AO가 없으면 프레임이 더 빨라 큐 압력이 다르게 걸린다.)

## 5. 결론

| 판정 항목 (§14) | 결과 |
|---|---|
| 60fps 목표 | **충족** — 중앙 3.1 ms, 여유 5.4배 |
| 30fps 미만 지속 구간 없음 | **충족** — 25 ms 초과 프레임 0% |

**아트 작업 예산이 확보되었다.** 다음 항목은 성능을 이유로 미룰 필요가 없다.

- 벽/아크릴 실사 텍스처 (현재는 절차적 노이즈) — 텍스처 샘플링 추가는 dpr 결과로 보아 거의 공짜
- 집게 3D 모델 교체
- 구슬 로고 데칼

**남은 리스크는 하나뿐**: 위 수치는 전부 개발 PC 값이다. 설치 PC가 이보다 5배 이상 느리면
결론이 뒤집힌다. 실기기 확보 즉시 위 두 명령을 돌려 §2 표를 교체하고,
그때 처음으로 품질 프리셋 하향이 실제로 필요한지 판단한다.

## 6. 도구 사용법

```bash
node tools/bench.mjs                      # 전체 매트릭스 (헤드룸)
node tools/bench.mjs --vsync              # 60Hz 고정 (끊김 확인)
node tools/bench.mjs --only balls          # effects | presets | balls | dpr
node tools/bench.mjs --seconds 20          # 조합당 측정 시간
node tools/bench.mjs --out reports/x.csv   # CSV 출력 경로
```

측정 조합은 런타임 오버라이드로 주입한다 — 앱 코드를 고치지 않고 조합을 바꾼다.

| 전역 변수 | 대상 |
|---|---|
| `__Q_DPR__` / `__Q_BLOOM__` / `__Q_DOF__` / `__Q_AO__` / `__Q_SHADOWS__` | `layout.ts` `QUALITY.high` 개별 항목 |
| `__Q_LEVEL__` | 품질 단계 고정 (`high`\|`mid`\|`low`). 고정 시 §13 자동 축소도 멈춘다 |
| `__BALL_COUNT__` | 서버가 준 구슬 수를 덮어쓴다 |
| `__DEPTH_GLASS__` / `__DEPTH_CS__` | 전면 유리 / 접지 그림자 |

벤치는 매 조합마다 플레이 도중 페이지를 닫으므로 미완료 세션이 남는다.
다음 조합 진입 시 운영자 패널에 복구 화면이 뜨면 **무효 처리**를 먼저 누른다.
이 처리가 없으면 시작 버튼을 못 찾고 어트랙트 화면(=항상 60fps)을 측정하게 되는데,
초기 측정에서 실제로 이 함정에 빠져 모든 조합이 58.9fps로 똑같이 나왔다.
지금은 게임 화면 진입에 실패하면 그 조합을 **실패로 처리하고 표에서 제외**한다.
